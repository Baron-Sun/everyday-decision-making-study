# Concurrency verification — 2026-09-05

The final comparison uses real PostgreSQL 17.9, an anonymous role with a 3-second statement timeout, and the production `claim_advice_transfer_assignment_same_post` RPC with opinion-difficulty responses. It replays the historical migration chain before testing the checked concurrency upgrade twice. Every simultaneous operation has its own preconnected database backend. All study records are synthetic and local.

| Scenario | Historical source | Upgraded source |
| --- | --- | --- |
| 100 simultaneous arrivals | 100 assigned; p95 766 ms | 100 assigned; first response p95 261 ms; including retry p95 2,135 ms |
| 200 simultaneous arrivals | 100 assigned, 100 quota wait; p95 1,098 ms | Same admission split; first response p95 262 ms; including retry p95 2,173 ms |
| 500 simultaneous arrivals | 100 assigned, 400 quota wait; p95 2,090 ms | Same admission split; first response p95 295 ms; including retry p95 2,488 ms; maximum 4,108 ms |
| One participant row held; 40 unrelated requests | 7 unrelated 3-second timeouts; p95 3,005 ms | 0 unrelated errors; p95 213 ms |
| 20 expired reservations, a stale queue head, 200 newcomers | All 200 waited while 20 tokens remained available | 20 replacements assigned, 180 quota wait; each cell again has 5 committed tokens |
| 100 concurrent phase-1 / phase-2 saves | p95 248 / 258 ms | p95 65 / 70 ms |
| 100 heartbeats + 100 drafts + 200 arrivals | 0 terminal errors | 0 terminal errors after bounded retry |
| 100 finals + 100 duplicate retries + 100 heartbeats | Exactly 100 submissions | Exactly 100 submissions; 5 per cell; no terminal errors after retry |

The upgraded 500-arrival test used at most three attempts (two retries). Busy responses are deliberately handled with randomized delay; they are included in total participant wait. The updated behavior favors quick feedback and recovery from contention, so it can increase end-to-end latency for uncontended work on a fast local machine. Quota wait after all 100 slots are occupied is expected capacity handling.

The suite also passed concurrent same-participant resume, revived-standby priority, and 30 identical comprehension-event retries counting as only one wrong answer. Formal assignments, quota ownership, all 20 cell limits, submission uniqueness, and the exact five-completions-per-cell result were inspected.

Migration validation passed the four existing SQL acceptance scripts against the baseline, full upgrade, checked upgrade and fresh setup. Both upgrade routes are idempotent and preserve permissions and recruitment settings. Unexpected installed source aborts the checked upgrade atomically, including earlier changes in the same transaction. The five known live historical function variants are accepted and end at the expected canonical hashes. Historical helpers outside the concurrency patch remain unchanged and match between full and checked live upgrades.

A genuine upgrade regression installs the old server functions and locks historical phase answers before migration. After either upgrade, those answers and lock timestamps remain identical, final submission succeeds, duplicate submission is idempotent, and partially present or wrong audit metadata remains rejected. No immutability trigger is disabled.

Primary evidence: `baseline-same-post-20260905.json`, `after-same-post-20260905.json`, `migration-validation-20260905.json`. Earlier `baseline-20260905.json` and `after-20260905.json` used the A-to-B wrapper and are supplementary only.

These results verify SQL locking, retry recovery and quotas on a local server. They do not benchmark Supabase Nano hardware, PostgREST, the pooler, TLS, mobile networks, GitHub Pages delivery, or participant behavior, and they do not establish a production concurrency ceiling or guarantee zero Prolific returns. Connection establishment happens before each SQL burst and is excluded from request timings.
